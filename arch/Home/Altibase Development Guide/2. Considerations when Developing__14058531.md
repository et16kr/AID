This chapter summarizes considerations needed during development.

## **Choosing DBMS connection type**

### ① **Choosing ALTIBASE connection type**

| Connection Type | Description |
| --- | --- |
| CONNTYPE=1 | TCP/IP connection type, normal connection method |
| CONNTYPE=2 | UNIX Domain Socket connection type, only available in the local server |
| CONNTYPE=3 | IPC connection type, only available in the local server |

`CONNTYPE=n` specifies the connection type. When the connection string is specified in the program, the user can specify it explicitly. If the DBMS and application are located on different servers, only `CONNTYPE=1` can be used. If the DBMS and application run on the same server, `CONNTYPE=2` or `CONNTYPE=3` is recommended to reduce network communication cost.

### ② Auto-commit mode is the default setting for ALTIBASE

JDBC connects in auto-commit mode according to the standard specification. Other applications are determined by the `AUTO_COMMIT` property in the `$ALTIBASE_HOME/conf/altibase.properties` file by default unless the user changes it. If this property value is `1`, it operates in auto-commit mode. Auto-commit means that commit is automatically performed after a change transaction completes normally.

To change this property value to non-auto-commit, change the property value to `0` in the configuration file and restart ALTIBASE. To control auto-commit by session, execute the following SQL after connecting to the DBMS.

```
ALTER SESSION SET AUTOCOMMIT = FALSE; (In Java, control it by using the setAutoCommit function.)
```

(`ALTER SYSTEM` can change the setting in real time for the whole system, but the value is restored after restart. For settings that affect the whole system, modify the property file and restart ALTIBASE.)

## **Thread program, connection pool management**

In a threaded program, if multiple threads share one connection, the developer must perform concurrency control for that connection. ALTIBASE exchanges defined protocols during communication between a session and the server. The typical sequence is `PREPARE -> BIND -> EXECUTE -> FETCH`; if another protocol interrupts while this sequence must proceed in order, session processing can fail and an error can occur.

```
Communication link failure (EXEC->INVL)

Communication link failure (PREP->EXEC)

Invalid request to process the SQL statement
```

The above errors occur when another SQL statement is executed through one connection without concurrency control while that connection is already executing SQL in a threaded program or connection pool. Therefore, when these errors occur, first check whether the connection handling in the developer-written program has a concurrency-control problem or an incorrect interrupt during processing.

(Occasionally, if a timer is set in the user program, these errors may occur even when the cause is not the concurrency-control problem described above. For example, if a timer operates during the `SELECT` to `FETCH` process and another SQL statement is executed before the `FETCH` protocol completes, the above errors may occur.)

## **Checkpoints when disconnecting an application**

The SQL statements executed in the program are prepared in individual programs and servers. It is recommended to develop code to release resources when these SQL statements are used. In particular, in the case of Java, memory increase may occur, so the following code is important.

```
Connection con = pool.getConnection();
Statement stmt = con.createStatement();
ResultSet rs = stmt.executeQuery();

try
{
   ….
} exception ()
{
   …..
}
finally
{
    // Release all resource used within the program.
    rs.close();
    stmt.close();
    conn.close();
}
```

In CLI/ODBC development, after memory is allocated with `SQLAllocStmt`, `SQL_DROP` must be executed through the `SQLFreeStmt` function when use is complete. When reusing the statement, use the `SQL_CLOSE` option. To release it completely, use the `SQL_DROP` option to explicitly release the resource.

## **Session Timeout**

A session means a program connection to the DB. Each session is managed by ALTIBASE timeout policies. ALTIBASE provides the following timeout policies. The options highlighted in the Korean source can be controlled only in the connection string.

|  | Session state after an error | **Description** |
| --- | --- | --- |
| CONNECTION_TIMEOUT | Disconnected | Option to set the timeout in the blocked state between transmission/reception on the network while connected to the DB |
| TIMEOUT | Disconnected | Occurs when the time to try to connect to the DB exceeds this setting |
| QUERY_TIMEOUT | Connected | Occurs when the total time to execute a query while connected to the DB exceeds this setting |
| FETCH_TIMEOUT | Disconnected | Occurs when the time interval during which the FETCH protocol occurs exceeds this value after executing the SELECT statement while connected to the DB |
| IDLE_TIMEOUT | Disconnected | Occurs when idle time without executing any query while connected to DB exceeds this setting |
| UTRANS_TIMEOUT | Disconnected | Occurs when this setting value is exceeded until commit/rollback is executed after executing the query while connected to the DB (execution query is rolled back) |

To set a 5-second time limit for connection attempts and disconnect when there is no response within 30 seconds during network blocking, add options to the connection string as follows.

```
DSN=127.0.0.1;CONNTYPE=2;TIMEOUT=5;CONNECTION_TIMEOUT=30
```

Other `TIMEOUT` settings operate in the units configured in `$ALTIBASE_HOME/conf/altibase.properties`, and can be controlled per session by executing the following queries. Setting a value to `0` means unlimited.

```
ALTER SESSION SET QUERY_TIMEOUT = 30 -- Unit: seconds
ALTER SESSION SET FETCH_TIMEOUT = 30
```

If the error by TIMEOUT occurs, the following error can be checked in the application.

|  | Error Message |
| --- | --- |
| CONNECTION_TIMEOUT | Connection time out |
| FETCH_TIMEOUT | The session has been closed by the server |
| IDLE_TIMEOUT | The session has been closed by the server |
| QUERY_TIMEOUT | Client's query exceeded in the execution time limitation |
| TIMEOUT | Client unable to establish connection |
| UTRANS_TIMEOUT | The session has been closed by the server |

TIMEOUT-related errors are also recorded in `$ALTIBASE_HOME/trc/altibase_boot.log`.

```
[2010/07/06 13:10:35] [Thread-182894171744] [Level-1]
[Notify : UTrans Timeout] Session Closed by Server : Session ID = 53
CLIENT_INFO => TCP 127.0.0.1:3992(PID : 13645)
Time Limit => 3
Running Time => 5
Last Query => insert into t1 select * from t1 limit 1
Caused by Transaction => 82368
```

If the above log is recorded in altibase_boot.log, the developer must check and take action to determine why the Timeout error occurred.

Each cause is as described above. If the timeout is caused by a query-processing bottleneck, tune the corresponding query. If `UTrans_Timeout` occurs as in the example above, commit/rollback was not performed after a change transaction occurred, so use the connection information to correct the transaction-control logic in the corresponding program.

If the above actions are difficult and business processing must be forced, change the `TIMEOUT` setting for the program's DB session rather than changing the property value for the whole DB.

## **Considerations when using SELECT Cursor**

When implementing a SELECT statement using CURSOR, the user must perform an error check on the FETCH statement and close the CURSOR after an error occurs or after reading all data. If the user tries to FETCH a CURSOR that has already been read or try to work on a CURSOR that is not closed yet, an unintended error may occur. After using CURSOR, you must CLOSE normally.

Another consideration is that in the case of ALTIBASE, if COMMIT/ROLLBACK occurs during FETCH, the open CURSOR is automatically closed. Therefore, in order to create another transaction while during FETCH, a separate DB session needs to be created and a separate transaction needs to be processed with the session or perform a COMMIT/ROLLBACK after all the FETCH is completed.

However, if there are a large number of records to be processed, it is recommended to implement a structure in which separate sessions are established and processed rather than bulk changes. If the number of records to be changed must be bound in one transaction, it is recommended to develop a program so that conditions can be separated and processed.

Refer to the conditions for the bulk change operation below.

## **Checking SQL Error**

Developers in an ALTIBASE environment should check SQL errors after every query is processed. In particular, the following cases must be checked to identify errors clearly.

```
EXEC SQL PREPARE ….
EXEC SQL EXECUTE ….
If (SQLCODE != SQL_SUCCESS)
   Error_log ();

Or,
EXEC SQL DECLARE CURSOR…
EXEC SQL OPEN ….
If (SQLCODE != SQL_SUCCESS)
   Error_log ();
```

In the above code, there is no error checking after performing PREPARE or DECLARE CURSOR. In this case, if the PREPARE (DECLARE CURSOR) step causes an error, the SQL error in the EXECUTE (OPEN) step would cause an error such as "Not defined (XX)", and despite the fact that it was actually caused by the PREPARE (DECLARE CURSOR) error, but the error cannot be accurately confirmed.

ALTIBASE also sends a query to the server during `PREPARE` or `DECLARE CURSOR`, and processes the query up to the step before execution.

It is important to note that SQL error checking must be performed when all SQL processing statements are entered.

## **Considerations for LOB type**

When querying for LOB type in ALTIBASE, it must be operated in non-auto-commit mode. The following error may occur in auto-commit mode.

```
[ERR-91101 : Connection is in autocommit mode. One can not operate on LOB data with autocommit mode on.]
```

Queries that exclude LOB columns are not affected, but the above error occurs when a LOB type is included in the `SELECT` target list. Therefore, when querying LOB types, change the session property to non-auto-commit mode before execution.

However, in the case of using ALTIBASE HDB 6.3.1 or later JDBC driver, LOB type data can be queried in auto-commit mode by setting the transaction commit mode to be controlled on the client-side. How to set the transaction commit mode on the client-side of the JDBC is as follows.

- Example of `altibase_cli.ini`

```ini
[ DataSource ]
Server=192.168.1.1
Port=20300
User=SYS
Password=MANAGER
AlternateServers=(192.168.1.2:20300,192.168.1.3:20300)
ConnectionRetryCount=3
ConnectionRetryDelay=5
LoadBalance = On
SessionFailOver = Off
ClientSide_Auto_Commit = On
```

## **Using Prepared Statement**

ALTIBASE stores execution plans for internally executed queries to speed up query processing. If a query is executed with `PREPARE`/`EXECUTE` every time, the already prepared execution plan is used internally, but the network cost for `PREPARE` is still incurred every time. To avoid this performance decrease, write code in the following form.

|  |  |
| --- | --- |
| ( O )<br>`Prepare statement`<br>`while (1)`<br>`{`<br>`Execute statement`<br>`}` | ( X )<br>`while (1)`<br>`{`<br>`Prepare statement`<br>`Execute statement`<br>`}` |

Among open source DB development libraries, OTL (Oracle, ODBC Template Library) processes every query by performing `prepare`/`execute` each time. However, when the streaming option is enabled, a query that has been prepared once is processed by execution only. This tuning factor, which reduces network transmission cost, can improve application processing speed by more than two times. Developers should minimize dynamic SQL where possible during query processing and check whether the same query is being prepared every time.

```
sprintf (sql,  “INSERT INTO t1 VALUES (%d, %d)”, szNum1, szNum2);
EXEC SQL Prepare S for :sql;
EXECUTE S;
```

The above code creates an SQL statement to be executed each time, prepares it, and executes it. In this case, the following would be reasonable.

```
EXEC SQL INSERT INTO t1 VALUES (:szNum1, :szNum2);
```

## **SQL Tuning**

When developing operations related to DB operation, there are cases where query processing is slow. Or, there are cases where the query was processed quickly in the test environment, but the query process is very slow in the integration test or operation stage. This can be seen as a case where the developer or DBA neglects the verification or testing process of the execution plan for all queries executed.

ALTIBASE can check the query processing process, that is, the execution plan as follows.

```
ALTER SESSION SET EXPLAIN PLAN = ON;
```

After executing the above command, the execution plan can be checked by executing a query in iSQL or a utility such as AdminCenter2.

```
iSQL> ALTER SESSION SET EXPLAIN PLAN = ON;
Alter success.
iSQL> SELECT a, COUNT(*) FROM t1 WHERE a = 1 GROUP BY a;
A           COUNT
------------------------------------
1           262145
1 row selected.
------------------------------------------------------------
PROJECT ( COLUMN_COUNT: 2, TUPLE_SIZE: 16 )
 GROUP-AGGREGATION ( ITEM_SIZE: 32, GROUP_COUNT: 1, BUCKET_COUNT: 1024, ACCESS: 1, SELF_ID: 3, REF_ID: 2 )
  SCAN ( TABLE: T1, FULL SCAN, ACCESS: 262145, SELF_ID: 2 )
------------------------------------------------------------
```

The execution plan above shows that table `T1` was full-scanned and that 262,145 records were accessed. If an index exists and the condition is specified so the index is used, output like the following may appear.

```
------------------------------------------------------------
PROJECT ( COLUMN_COUNT: 1, TUPLE_SIZE: 4 )
 SCAN ( TABLE: T1, INDEX: IDX_T1, ACCESS: 2, SELF_ID: 2 )
------------------------------------------------------------
```

For more information on SQL tuning, refer to the `ALTIBASE SQL Tuning Guide`. Developers should read it before development.

## **Cautions during the bulk change operation**

General bulk change operations cause high load not only in ALTIBASE but also in other DBMSs, and each vendor has required precautions. ALTIBASE requires the following cautions.

### ① Possibility of memory increase in case of mass change of memory table

ALTIBASE supports the MVCC (Multi-Version Concurrency Control) technique. In the MVCC technique, when a change occurs, the same record is duplicated in the empty space of the table to make the change. If 10 million changes are made, memory increases due to 10 million copies will inevitably occur. (Of course, the increased area is reused as data or replication area, but the memory is not released in real time.)

### ② Continuous increase of transaction log files by performing bulk change operation

A large number of changes require a redo log for each change target record to be recorded in the transaction log file. Therefore, it is necessary to record the redo log of all the records that are changed in one transaction, but if the scope of this target is large, as many transaction log files are created as well. (ALTIBASE deletes the transaction log file at the time of the checkpoint. If there is information on which the transaction is ongoing in the log file, it cannot be deleted, and there is a possibility of a disk shortage failure due to the log file increase.)

### ③ Possibility of dead-lock occurrence and delay in the reflection in a replication environment

In a replication environment, as described above, the change information of all records changed by one transaction is transmitted to the other server.

In this process, a lock is held for the corresponding record on the peer server. If the peer server changes records in the same range, a deadlock can occur between the transaction caused by the replication log and the transaction generated on the peer server itself.
