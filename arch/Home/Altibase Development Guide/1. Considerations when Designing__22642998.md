This chapter describes considerations when designing a DB or system using ALTIBASE. Items missed during the design stage can have a significant impact on later development and operation, so use the following items as design references.

## **Considerations for replication environment**

### ① ALTIBASE network-based replication method

ALTIBASE adopts a network-based replication method that synchronizes data by sending and receiving changed transaction logs. In other words, it is not a disk-sharing method that users commonly expect. Therefore, replication design must account for data transmission delay that can occur in a network environment.

ALTIBASE replication supports Lazy and Eager methods. The Lazy method allows data transmission delay, while the Eager method does not allow it. The Lazy/Eager setting can be configured per replication unit. Therefore, use the Lazy method for workloads that can tolerate data transmission delay, and use the Eager method for workloads where data synchronization is required.

| **Comparison** | **Lazy Method** | **Eager Method** |
| --- | --- | --- |
| Performance | 90% performance level of a single server | Performance degradation compared to the Lazy method |
| Synchronization | This structure checks only whether the changed transaction log was transmitted successfully to the peer server, so performance is good but synchronization may be delayed. | To prevent data inconsistency on the peer server, the transaction is committed locally only after it is committed on the peer server. Performance is delayed, but synchronization is guaranteed. |

### ② Consider measures to prevent data inconsistencies

In a dualized environment, if records with the same primary key are modified simultaneously with different values on both servers, unwanted data inconsistency may occur due to server conflicts. To prevent this, the following design considerations are required:

a. Business Logic Separation

Modification operations (Insert/Update/Delete) must be executed only on one server within the group, while the other server is used exclusively for read operations. For example, assigning server A as read-only for real-time queries and server B as write-only for modification tasks can fundamentally reduce the risk of conflicts.

b. Data Responsibility Separation by Server

To avoid simultaneous updates to the same PK, divide and manage the PK range by server. Example: Design so that odd-numbered member IDs can only be modified on server A, and even-numbered IDs only on server B.

### ③ Log-based replication method

Altibase replication sends the change logs of transactions generated on the local server to the remote server. If one SQL statement changes one million rows, one million changed transaction logs are transmitted to the remote server, rather than one SQL statement.

For other major considerations in a replication environment, also refer to the ALTIBASE technical documents [Altibase Replication Configuration Guide](https://docs.altibase.com/pages/viewpage.action?pageId=13828098) and [Altibase Replication Constraints Guide](https://docs.altibase.com/pages/viewpage.action?pageId=19333729).

## **Consideration for high availability (HA) and backup**

Under normal circumstances, when a failure occurs and recovery is performed, replication automatically synchronizes data by sending a transaction log to the other side that has not yet sent to the point of failure. However, due to the nature of the network, it is necessary to consider whether there is a task that cannot perform a fail-over service immediately due to data inconsistency caused by the inability to transmit the change transaction log at the time of failure.

If a service can be provided only after data is synchronized, ALTIBASE provides an Off-Line replicator to apply unsent data. However, it can be used only when the failed server's disk is accessible. To use this function, building shared disk equipment is recommended.

If the Off-Line replicator cannot be used, establish an HA policy in which the program accumulates raw data at the failure point and applies only the necessary portion to the normal server before transferring service. For example, in securities systems, all data sent to external systems is often managed by unique numbers. Because those numbers exist both in the external system and in the DB, some business logic applies only the difference between the external system and the DB system to the normal server after a failure.

In addition to HA, it is necessary to establish a backup policy for data file damage caused by physical disk failure and failure caused by transaction log file corruption. The Altibase backup method provides both full and incremental backup methods using the archive mode.

Therefore, users must choose one of the following backup methods: (1) cold backup of all necessary files while offline, (2) full backup of the database or tablespaces while online, or (3) incremental backup of the database or tablespaces while online.

The backup method should be one of the following types.

| Method | Description |
| --- | --- |
| iLoader Backup | Only snapshots of records are stored for each major table. Only data at the time of backup by iLoader is backed up |
| Cold Backup | After the ALTIBASE process is shut down, all necessary files are copied and stored. Recovery is possible only up to the point when the files were copied. |
| Archive Full Backup | Because the entire database image including transaction log files is backed up at the time of backup, recovery is possible to the point where there is no damage to the files. |
| Archive Incremental Backup | A full backup is performed once at the beginning, and only changed images are backed up afterward. Transaction log files are also backed up, so recovery is possible until the point where no files are damaged. The more incremental backups there are, the longer recovery takes, so this must be reviewed. |

For backup, refer to [Considerations for Altibase Backup Policy](https://docs.altibase.com/pages/viewpage.action?pageId=14057586).

## **Considerations for designing table**

### ① Select the storage location of the table according to the purpose

ALTIBASE supports both memory and disk tablespaces. Select the storage location according to the purpose and workload characteristics of each table.

1. Memory tablespaces are suitable for workloads that require very high processing performance. They are recommended for tables with frequent transactions and short data validity periods, such as session information or same-day transaction data.
2. Disk tablespaces are suitable for workloads that require long-term retention and loading large volumes of data. They are mainly used for historical data and tables that are queried in large volumes.
3. Hybrid Partitioned Table (HPT) can be used to configure one logical table with both memory and disk partitions. For example, the latest N days of data can be stored in memory partitions and older data can be stored in disk partitions, while the table is managed as a single table. Applications can query one table without distinguishing separate tables, which improves manageability. However, even when Hybrid Partitioned Table is used, queries that include disk partitions are still affected by disk I/O performance.

### ② Considerations for Column type

In the case of the numeric type provided by ALTIBASE, a type such as Numeric (9) can be sufficiently expressed as an integer type, but occupies 8 bytes of space. It occupies 4 bytes per record more than integer type. In terms of processing performance, numeric internally incurs the cost of converting back to native type, which is somewhat slower than the integer type.

## **Limitation of partition table**

For the ALTIBASE partition table (as of version 7.3.0), partitioned local indexes and non-partitioned global indexes are supported, and partitioned global indexes are not supported. Therefore, it is recommended that partition tables be used to separate and store historical data by month or business purpose because a significant performance decrease can occur when querying the entire partition table without including the partition key in the condition clause.

## **Considerations for Hardware preparation**

The hardware-related considerations to the information above are summarized and explained in this section.

|  |  |
| --- | --- |
| **Consideration** | **Description** |
| Replication | Because replication uses the network, connecting servers directly with a separate Giga-bit LAN card or using a private network is recommended. |
| Disk | When considering backup, in addition to the estimated DB capacity, disk space is required to store more archive log files along with the entire tablespace. |

In addition, ALTIBASE's redo log file policy can be viewed as unlimited creation. ALTIBASE does not create a fixed number of redo log files and reuse them; it continuously creates new redo log files. Because bulk change operations can inevitably create many redo log files, allocate enough disk space for the redo log file location.

For more detailed information about hardware capacity estimation, refer to the `ALTIBASE Capacity Estimation Guide`.
