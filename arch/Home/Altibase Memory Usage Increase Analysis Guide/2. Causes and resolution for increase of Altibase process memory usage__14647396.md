Memory increases caused by processes other than Altibase are not covered in this document. This chapter describes how to respond to increases in Altibase process memory usage.

As mentioned in the previous chapter, the memory increase of Altibase can be organized as follows:

1. When data in the memory table is increased
2. When the number of executing SQL statements increases
3. When it is increased by the MVCC (Multi-Version Concurrency Control) technique
4. When the deletion of aging target information is delayed

## **1. When data in the memory table is increased**

The trend of memory data usage increase can be checked with the SQL statement below.

```
set linesize 100;
set colsize 30;
SELECT A.TABLE_NAME
     , (B.FIXED_ALLOC_MEM + B.VAR_ALLOC_MEM) ALLOC
     , (B.FIXED_USED_MEM + B.VAR_USED_MEM) USED
  FROM SYSTEM_.SYS_TABLES_ A ,
       V$MEMTBL_INFO B
 WHERE A.TABLE_OID = B.TABLE_OID
   AND A.TABLE_TYPE = 'T'
 ORDER BY 2 DESC;
```

Among the results from the above query, 'Alloc' includes both space where data is stored and the available space. ('Used' means only space where data is stored.)

If the user deletes around `900M` after loading `1G` of data, the table still has `1G` of allocated space, `100M` of used space, and the remaining `900M` as empty space usable only by that table.

The part that confuses many Altibase users is this `900M`. Because the data was deleted, users often expect this space to be freed by Altibase or the OS and expect memory usage to decrease.

Most OS memory management structures do not immediately return memory to the OS even if a program frees memory that was allocated once. In practice, they generally reserve the freed area in memory and use that free area when another application runs out of memory. In other words, because memory allocation and deallocation are costly, frequent memory allocation/free operations are avoided as much as possible.

This algorithmic concept applies equally to Altibase. Altibase also keeps the used space as reusable space in the table even if data is deleted.

If the user finds such a table, take the following actions.

1. Compact the table. Memory tables are allocated space from a memory tablespace. However, if space increases because a large amount of data was loaded into and deleted from one table, other tables in the same memory tablespace may not have enough allocatable space. Unused space in a table can be returned so that other tables in the same memory tablespace can use it. This is called compaction.

  ```
  ALTER TABLE table_name COMPACT;
  ```
2. Restart Altibase.

  These actions make it possible for other tables in the same memory tablespace to be allocated space. However, the memory usage occupied by the OS still does not decrease. In this case, restarting Altibase can have the same effect as reducing memory usage for the following reason.

  In the restart process, the data pages of all memory tablespaces are loaded into memory, but empty pages that are not actually written to are not loaded into memory, thus reducing memory usage.

  If it is difficult for the user to perform compaction on each table, the compaction effect can be obtained by restarting Altibase during regular preventive maintenance (PM).

## **2. When the number of executing SQL statements increases**

The user can periodically check the number of queries recorded in `V$STATEMENT`. The queries recorded in `V$STATEMENT` are not exact because only queries executed by currently connected sessions are recorded, but they are useful for estimating the approximate count.

In this case, there is no special action for the user to take if the increase is caused by queries required for business purposes. However, the following items often need to be checked with the developer.

1. Check whether all queries are closed after use. In general, after a query is used, the object for that query must be closed.

  Ex) JAVA/JDBC

  ```
  Connection cn;
  prepareStatement ps;
  ps = cn.prepareStatement ("select…");
  …
  ps.close();
  ```

  If a statement such as `ps.close` does not exist in the above code, Altibase internal modules such as `Query_Prepare` continue to maintain memory for the query. If this situation repeats, memory continues to be used unless the session ends. Even if Altibase frees memory that was used once, the OS does not immediately reclaim it, and as a result memory usage remains increased. Therefore, check whether objects used for query execution are released normally.
2. Check whether similar queries continue to be used. Consider the following example.

  ```
  SELECT 1 FROM DUAL WHERE C1 = 1;
  SELECT 1 FROM DUAL WHERE C1 = 2;
  SELECT 1 FROM DUAL WHERE C1 = 3;
  ```

  The above queries can be handled with one statement by replacing them with a statement such as `SELECT 1 FROM DUAL WHERE C1 = ?` and developing the application so that only the variable value in the query condition changes.

  If similar queries as above are accumulated and executed, the current version of Altibase allocates memory by analyzing each query as a different query.

## **3. When it is increased by the MVCC (Multi-Version Concurrency Control) Technique**

The MVCC technique refers to a general DBMS concurrency control method that improves performance by preventing read and change operations from waiting for each other. Currently, Altibase memory tables operate by creating a copy of a record at the time of a change operation and recording the changed information in that copy.

Therefore, when a record is changed, the original and the copy exist together. At the time of deletion, there is no memory increase of this type; an increase may occur due to aging delay.

This means that when a large change operation is performed, copies are created for as many records as are targeted by the change operation. This is a trade-off in which resource usage increases in exchange for high performance.

This copy is created in the space of the table. Therefore, when a large amount of change operation occurs, the usage of the table increases. If there is empty space in the table, the corresponding space is used, and if there is not enough space, space is allocated from the tablespace and used.

The user should use the usage result for each table to identify tables where the difference between `Alloc` and `Used` is excessive, and take action if abnormal usage is found during operation. The available measures are table compaction or restart, as described earlier. Also, because large change operations are generally not recommended for DBMS work, perform change operations in batches of a certain number of records.

For example, if ten million records must be changed, divide the work into units of tens of thousands of records and perform the changes in batches by using the `LIMIT` clause.

## **4. When the deletion of aging target information is delayed.**

The original record becomes a deletion target because the copy created by MVCC becomes the final record at commit time.

If a rollback occurs, the copy becomes the deletion target. These records to be deleted are called `Old Version` or `Garbage Data`. The deletion operation is internally called aging, and an internal module called GC (Garbage Collector) handles it.

The problem is that there may be cases in which the deletion targets cannot be deleted for some reason. If this state persists, the deletion targets will continue to accumulate, which may cause an increase in memory usage.

Whether GC is aging records normally can be checked with the following query.

```
SELECT ADD_OID_CNT, GC_OID_CNT FROM V$MEMGC;
```

`ADD_OID_CNT` refers to the targets that transactions handed over for aging.

That is, it is the same as the number of transactions that requested aging. `GC_OID_CNT` means the number of aging targets processed by GC.

If the above values continue to change, GC can be considered to be working normally even if processing is delayed. However, if `GC_OID_CNT` does not increase at a specific point in time, a problem can be considered to have occurred.

The GC module can delete the record only if the record to be deleted is not referenced by any transaction, and the delete target list can be deleted only in the order requested.

Therefore, if a GC problem is suspected, the issue is usually that a transaction still remains unfinished. Find and clean up the corresponding transaction.

The transaction can be found with the following query.

```
SELECT A.SESSION_ID,
       B.QUERY
  FROM V$TRANSACTION A,
       V$STATEMENT B,
       V$MEMGC C
 WHERE A.ID = B.TX_ID
   AND (A.MEMORY_VIEW_SCN = C.MINMEMSCNINTXS
        OR A.MIN_MEMORY_LOB_VIEW_SCN = C.MINMEMSCNINTXS);
```

When the above query is executed, it displays information about the problematic query, including the monitoring query itself.

If a query other than the monitoring query is displayed and its execution time is excessive, tune that query. If the user did not terminate normally after executing the query, check the program source and make it terminate normally.

※ Memory increase related to MVCC and GC is limited to the memory table.
