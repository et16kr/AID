# How to check system memory/swap by OS

---

Use OS commands to check available memory and determine whether the system has insufficient free memory.

The memory usage can be checked with the following OS command.

| size | The number of pages in the total physical memory. Actual 1 page is 4,096 bytes, so it is a system with 7936M of memory |
| inuse | The number of physical memory pages in use (Computational + Persistent) |
| free | The number of pages not in use in physical memory |
| pin | The number of pages of physical memory that cannot be swapped out |
| virtual | The number of pages created by VMM (Virtual Memory Manager) |
| pg space | The usage of paging space |

## Routine Checklist

The user needs the following history to determine whether current memory usage is normal. When a problem occurs, this history can be used as important information for tracking the cause by analyzing what increased compared with normal usage.

| Item | Collection Plan |
| --- | --- |
| Hourly/daily memory utilization | Periodically record and manage the memory utilization rate of the Altibase process by using the method provided by the OS. |
| Transaction throughput by time/day | Record and manage the transaction throughput of the application. If this is difficult, periodically collect and record the following information from `V$MEMSTAT` provided by Altibase.<br>```<br>select * from v$memstat order by alloc_size desc;<br>``` |
| Increase or decrease in the service thread | Service threads may increase because sessions or workload are higher than usual. Check whether this pattern occurs.<br>`SELECT COUNT(*) AS THREAD FROM V$SERVICE_THREAD; SELECT COUNT(*) AS SESSION FROM V$SESSION;` |

It may be more convenient to record information collected at regular intervals in a file using the following shell script.

Since `EXECUTE COUNT` obtained from `V$SYSSTAT` is cumulative, calculate the increase per unit time as `(recent value - previous value)`.

```
# gettps.sh
ALTIPID=`ps -ef | grep $USER | grep  "bin/altibase -p boot"  | grep -v grep | awk '{print $2}'`
MAXCOUNT=3
COUNT=0
INTERVAL=30

do_getExecuteCount()
{
  is -silent <<EOF
  set linesize 1024;
  set colsize 50;
  set feedback off;
  set heading off;
  select 'RESULT='||( select count(*) from v\$session )
       ||'=' || ( select count(*) from v\$service_thread )
       ||'=' || ( select sum(value) from v\$sysstat where name in ( 'execute success count','prepare success count','prepare failure count') )
  from dual;
EOF
}
while [ $COUNT -lt $MAXCOUNT ]
do
  ALTICPU=`ps -o pcpu -p $ALTIPID | grep -v CPU`
  ALTIMEM=`ps -o pmem -p $ALTIPID | grep -v MEM`
  EXECRESULT=`do_getExecuteCount`
  SESSIONCNT=`echo $EXECRESULT | grep "RESULT=" | cut -d'=' -f 2| tr -d ' '`
  THREADCNT=`echo $EXECRESULT | grep "RESULT=" | cut -d'=' -f 3 | tr -d ' '`
  EXECCNT=`echo $EXECRESULT | grep "RESULT=" | cut -d'=' -f 4 | tr -d ' '`
  echo  `date "+%Y%m%d %H%M%S: CPU USAGE="`$ALTICPU" " MEM USAGE=$ALTIMEM" SESSIONCNT=$SESSIONCNT THREADCNT=$THREADCNT EXECCNT=$EXECCNT"
  sleep  $INTERVAL
  COUNT=`expr $COUNT + 1`
done
```

When the above shell script is executed, the following output can be displayed.


## **V$MEMSTAT**

V$MEMSTAT is a performance view of memory usage for each internal module provided by Altibase.

If the memory occupied by the Altibase process is large, the user can check Altibase's memory usage in detail with V$MEMSTAT.

| Item | Description |
| --- | --- |
| Query_Prepare | When executing SQL, memory is required during the prepare process to internally manage information such as SQL statement analysis, statistics information, execution plans, and bindings. In general, if an application executes SQL with a Prepare/Execute structure every time (Direct Execute method), memory usage for this item may increase.<br>If SQL is executed with the Prepare Execute method (1 Prepare + N Execute), memory usage for this item increases to some extent and then maintains a certain size during operation. This value is the total size of `Query_Prepare` used by all sessions. |
| Query_Execute | This is the memory size used to store data sort and intermediate result values during SQL execution.<br>This can increase when SQL is executed with a memory table or the `TEMP_TBS_MEMORY` hint. This value is the total size of `Query_Execute` used by all sessions. Memory is released when Altibase SQL execution ends. Therefore, in a normal case, it increases to some extent, then decreases, and maintains a certain size during operation. |
| Query_Binding | This is the memory size for storing binding variables during SQL execution. This value is affected by the binding variables used in one SQL statement. When the `PrepareStatement` is closed or the session is terminated, memory is returned, so it increases and decreases to some extent in normal cases and maintains a certain size during operation. Common examples of `Query_Binding` increase are as follows:<br>1) When statements increase rapidly<br>2) Binding for a very large data type<br>3) When `PrepareStatement` is not properly closed<br>4) When prepare statements are created repeatedly without limit while handling an exception |
| Storage_Memory_Manager | This is a space to store information for memory tablespace management and data in memory tables, and is the size of memory data residing in memory for Altibase's high-performance data processing. When memory data accumulates and grows, the value of this item increases. |
| Index_Memory | This shows the memory usage for indexes created on memory tables. An increase in this value means that memory index usage has increased. Memory can be cleaned up by removing indexes that consume a large amount of memory. |
| Storage_Disk_Buffer | This is memory used by the disk buffer manager. It is the space used to process data by buffering disk tablespace data in memory. If this space is insufficient, disk page in/out occurs frequently, which can degrade performance. |

## **Typical types of memory increase**

The memory increase of Altibase can be organized as follows based on the "Routine Checklist" described above.

1. When data in the memory table is increased
2. When the number of executing SQL statements increases
3. When it is increased by the MVCC (Multi-Version Concurrency Control) technique
4. When the deletion of aging target information is delayed

Let's take a closer look at the causes and measures for these cases in the next chapter.
