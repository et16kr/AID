## **Overview**

---

For internal monitoring of Altibase, it is necessary to understand meta tables and performance views, which are called the data dictionary. In this document, the relationship between meta tables and performance views is expressed using an entity-relationship diagram (ERD) for user understanding and convenience. This section explains the prerequisite concepts.

### About ERD Notation

For readability and query convenience, the ERD treats performance views as tables even though they do not have base tables. Join keys are marked as FK-style relationships. To avoid confusion caused by this notation, meta tables use a yellow background and performance views use a white background.

![image2016-7-13%209_28_9.png](https://docs.altibase.com/download/attachments/embedded-page/arch/2.%20Altibase%20Meta%20Table%20and%20Performance%20View%20Overview/image2016-7-13%209_28_9.png?api=v2)

In the ERD, columns that have the same attribute can have different names depending on whether they are in a meta table or a performance view, such as an `ID` column in a meta table and a `META_ID` column in a performance view. In that case, the same color indicates the same attribute.

### Note

It should be noted that Altibase meta table and performance view have the following characteristics.

1. Columns that have the same attribute can have different names depending on the meta table or performance view.
2. Depending on the Altibase server version, meta table and performance view column names can be changed or deleted.
3. Meta tables and performance views can be added or deleted depending on the Altibase server version.

### Terms

This is a definition of some of the terms that may cause confusion prior to explanation.

- Session

  This refers to the user's access unit connected to the Altibase server. One user can have multiple sessions at the same time
- Statement

  As a term that means each SQL executed in a transaction, 'SQL statement', 'Query', 'Query statement,' often has the same meaning depending on the context. In this document, it is unified as 'query'.
- Memory DB GC (Garbage Collector) or GC

  When the user executes commit, the record before the change maintained by the MVCC (Multi Versioning Concurrency Control) technique should be deleted. Altibase operates separate threads to delete records before changes, which are called memory DB GC and disk DB GC respectively. However, since the MVCC method of the disk DB has changed since Altibase 5.3.3, the disk DB GC disappears, so only the memory DB GC exists, so it is called GC or Ager.
