# Connection Failure

---

There may be a case when the DB cannot be accessed while the server or Altibase process is running normally. There can be five types of situations like this:

|  |  |
| --- | --- |
| **Type** | **Description** |
| User account restrictions | The following types of error logs can be recorded in $ALTIBASE_HOME/altibase_boot.log when a connection exceeding the number of file descriptors is attempted during the setup of the user account. |
| ERR-01052(errno=24) Unable to invoke open() function on [~~~] |  |
| ERR-71016(errno=24) Failed to invoke a system function, accept() Dispatcher failed callback |  |
| Altibase Hang status | This refers to a case in which connection is disabled due to a system or Altibase problem, and there is no DB access or response, or no new access. |
| Error in connection attempt | There may be cases in which the IP/Port number/Password of the server attempting to connect is incorrectly entered, and the lock status and TCP connection restrictions are set according to the password management policy. |
| ERR-50032 : Client unable to establish a connection. |  |
| ERR-31010 : User not found |  |
| ERR-4102E : Invalid password |  |
| ERR-31370 : The account is locked. |  |
| ERR-410E3 : The user cannot connect using TCP. |  |
| Network failure | In case of problems with LAN card or network settings |
| Insufficient disk space | Cannot write because disk space is insufficient |
| ERR-01052(errno=24) Unable to invoke open() function on [~~~] |  |
| ERR-01052(errno=24) Unable to invoke write() function on [~~~] |  |

Among the five types described above, the following four are user or hardware failures. First, check the following items.

|  |  |
| --- | --- |
| **Type** | **Checklist** |
| User account restrictions | The user account restrictions can be resolved by checking the result of `ulimit -n`, increasing this value, and restarting Altibase.<br>Generally, it is recommended to set the file descriptor value to `unlimited`, and it should be set to at least 4096. |
| Error in connection attempt | If there is an error in the connection attempt, the connection configuration must be checked.<br>Check whether the user account, password, or target IP address was entered incorrectly, and whether the attempted port differs from `PORT_NO` in `$ALTIBASE_HOME/conf/altibase.properties`. |
| Network failure | First, use `netstat` to check for packet errors. Then verify that normal `ftp`/`telnet` connections from other hosts to the host where Altibase is installed are possible, and that packet transmission and reception performance has not significantly degraded. |
| Insufficient disk space | Check disk usage with a command such as `df` (`bdf`), and then add the required disk space.<br>Caution:<br>Do not delete Altibase online log files. If online log files are deleted arbitrarily, the database cannot be recovered. |

The situation in which the system or Altibase Hang is questionable means that the Altibase process normally exists, but the connection attempt fails and there is no response to the previously connected DB session.

In this case, immediately collect the following information and request technical support from Altibase.

|  |  |
| --- | --- |
| **OS** | **Hang information acquisition method** |
| SUN | `/usr/sbin/pstack -F process_id > 1.txt`<br>`/usr/sbin/pstack -F process_id > 2.txt`<br>`/usr/sbin/pstack -F process_id > 3.txt`<br>Execute each command in order at 30-second intervals. |
| HP | This is not supported on PA-RISC, but IA series systems execute as follows.<br>`/usr/ccs/bin/pstack process_id > 1.txt`<br>`/usr/ccs/bin/pstack process_id > 2.txt`<br>`/usr/ccs/bin/pstack process_id > 3.txt`<br>Execute each command in order at 30-second intervals. |
| AIX | `/usr/bin/procstack -F process_id > 1.txt`<br>`/usr/bin/procstack -F process_id > 2.txt`<br>`/usr/bin/procstack -F process_id > 3.txt`<br>Execute each command in order at 30-second intervals. |
| Linux | If the kernel version is low, the command may not exist.<br>`/usr/bin/pstack process_id > 1.txt`<br>`/usr/bin/pstack process_id > 2.txt`<br>`/usr/bin/pstack process_id > 3.txt`<br>Execute each command in order at 30-second intervals. |

Commands such as `pstack` show the current status of all threads in the process with the specified process ID. Therefore, this can be used as important information for solving the problem.

(Similar to urgent failure, the system log and the Altibase trace log should be sent together.)

# **Failure due to insufficient resources**

---

Resources include all of the logical space used by Altibase from physical memory/disk space. This section describes how to respond to each situation that may occur during the operation.

## **Insufficient tablespace**

---

|  |  |
| --- | --- |
| **Type** | **Diagnostic method** |
| Insufficient memory tablespace | If the memory tablespace is insufficient, the following error occurs.<br>[ERR-110F1 : Unable to extend the tablespace(XXXXX) because the current size of tablespace(4194304K) becomes larger than MAXSIZE(4194304K) of the tablespace.] |
| Insufficient disk tablespace | If the disk tablespace is insufficient, the following error occurs.<br>[ERR-11123 : The tablespace does not have enough free space ( TBS Name :XXXXX ).] |

Since Altibase supports both memory DB and disk DB, the user must monitor usage for each. If the above error occurs because tablespace capacity is unexpectedly insufficient, take the following actions.

|  |  |
| --- | --- |
| **Type** | **Method** |
| Insufficient user memory tablespace | ```<br>ALTER TABLESPACE [tablespace name] ALTER AUTOEXTEND OFF<br>;<br>ALTER TABLESPACE [tablespace name] ALTER AUTOEXTEND ON MAXSIZE 1G<br>;<br>```<br>Execute the above commands in order. Since the tablespace name is specified in the earlier error message, specify that tablespace name. `MAXSIZE` must be set larger than the current `MAXSIZE`. |
| Insufficient SYS_TBS_MEM_DATA/SYS_TBS_MEM_DIC tablespace<br>or<br>If it cannot be resolved with the ALTER TABLESPACE command. | If the above error occurs in the SYS_TBS_MEM_DATA/SYS_TBS_MEM_DIC tablespace, it cannot be solved with the above method. In addition, it cannot be resolved when the total amount of all memory tablespaces has already exceeded the MEM_MAX_DB_SIZE value. In this case, after cleaning up unnecessary table data in the tablespace, execute the compact command, or if this method does not work, increase the MEM_MAX_DB_SIZE value in the $ALTIBASE_HOME/conf/altibase.properties file and then restart ALTIBASE.<br>```<br>DELETE FROM [table name]<br>;<br>TRUNCATE TABLE [table name]<br>;<br>ALTER TABLE [table name] COMPACT<br>;<br>``` |
| Insufficient disk tablespace | ```<br>ALTER TABLESPACE [tablespace name] ADD DATAFILE 'abcd.dbf' SIZE 1G AUTOEXTEND OFF<br>;<br>```<br>Since the tablespace name is specified when an error message displays earlier, specify the tablespace name. The name of the data file is designated by the user according to the naming rule, and the size is appropriately designated by referring to the size of another data file using the same tablespace. |

The response method for an error due to insufficient tablespace is an urgent measure. Afterward, it is necessary to check why the tablespace suddenly increased. The user must check the usage of DBMS objects belonging to each tablespace, review what changed, and remove the cause.

The usage of each object in the tablespace is described in detail in the "Altibase Monitoring Query Guide".

## **Insufficient physical disk space**

---

If the physical disk is insufficient, the DB status may seem like Hang because online log files that are essential for transaction processing cannot be recorded. In addition, there may not be any error message in the trace log because there are cases in which the Altibase trace log cannot be recorded due to insufficient space. Therefore, the user must periodically monitor the capacity of the physical disk. If a problem occurs, there is no way to do anything other than to free up space on the disk.

## **Insufficient physical memory space**

---

In case of insufficient memory, there is no separate countermeasure during the service. However, it is recommended to periodically collect the following results because the current status must be acquired.

|  |
| --- |
| ```<br>SET LINESIZE 1000<br>SELECT *<br>FROM   V$MEMSTAT<br>ORDER  BY MAX_TOTAL_SIZE DESC<br>;<br>``` |

The above query shows the current usage status of memory resources inside Altibase. With this information, it is possible to compare and analyze which module has a large memory increase with a periodic result log. (Comparison of results of the previous day/same day)

## **Impact of performing bulk change operation or long-running queries**

---

Altibase supports MVCC. MVCC is a technique that can improve DBMS performance by preventing waits between read and change transactions. (For more detailed information, refer to the "Altibase MVCC & GC Guide".) According to the implementation of MVCC, data targeted for deletion is retained as Garbage Data. If a bulk change operation or a long-running query exists, the data targeted for deletion cannot be removed until the corresponding transaction is completed. As a result, online log files or physical memory usage may increase. Long-running queries that cause this phenomenon can be checked as follows.

|  |
| --- |
| ```<br>SELECT *<br>FROM   V$STATEMENT<br>WHERE  TOTAL_TIME > 100000000<br>AND EXECUTE_FLAG = 1<br>;<br>```<br>This query retrieves queries that are currently being executed and execution time is more than 100 seconds.<br>```<br>SELECT SESSION_ID,<br>ID,<br>RPAD(QUERY, 150)<br>FROM   V$STATEMENT<br>WHERE  TX_ID = (SELECT ID<br>FROM   V$TRANSACTION<br>WHERE  MEMORY_VIEW_SCN IN (SELECT MINMEMSCNINTXS<br>FROM   V$MEMGC<br>LIMIT  1))<br>;<br>```<br>This query retrieves queries that have been executing for a long time to prevent the processing of the data to be deleted. |

For more detailed information, please refer to the "Altibase Monitoring Query Guide".

# Failure due to system problems

---

This section describes the type of error due to insufficient system resources.

|  |  |
| --- | --- |
| **Error type** | **Description** |
| Out of memory | Insufficient memory |
| Resource busy | Temporarily unable to access system resources |
| Too many open files | When the limit on the number of files that can be accessed at the same time is exceeded |
| No space left on device | Insufficient disk space |

If the above error types occur as a cause in the Altibase trace log, there are cases where the system error code is also recorded when an error message is recorded. It is also possible to check whether insufficient system resources occur with the corresponding system error code.

In addition, check the following logs to see if an error has occurred in the system.

|  |  |
| --- | --- |
| **OS** | System log to check |
| SUN | /var/adm/message file |
| HP | /var/adm/syslog/syslog.log file |
| AIX | errpt -a |
| Linux | /var/log/message file |

# Replication Failure

---

Altibase provides a data replication method using TCP/IP network for high availability. If there is any delay or other error during the service with replication, take the following actions.

|  |  |
| --- | --- |
| **Type** | **Description** |
| Replication sender/receiver problem | Sender/Receiver does not operate normally due to network error or replication setting error |
| Occurrence of data conflict | When data cannot be replicated because the data values in the DB between both ends are different |

Check the following replication Sender/Receiver problems.

|  |  |
| --- | --- |
| **Type** | **Method** |
| Existence of Sender | ```<br>SELECT COUNT(*)<br>FROM   V$REPSENDER<br>;<br>```<br>If the Sender is running normally, the result of the above query should be displayed as "1" or higher.<br>(Must exist as many as the number of replication objects.) |
| Existence of Receiver | ```<br>SELECT COUNT(*)<br>FROM   V$REPRECEIVER<br>;<br>```<br>If the Receiver is running normally, the result of the above query should be displayed as "1" or higher.<br>(Must exist as many as the number of replication objects.) |

Among the Altibase trace logs, various messages related to replication are recorded in "altibase_rp.log".

|  |
| --- |
| **Message when replication is running normally.**<br>[Recovery Sender] Replication REP1 Start... at [6030857] (Log of the Server that started replication) [Receiver] Replication REP1 Started ... (Log of the Receiver that received the command to start replication)  **If there is a problem with the Sender's connection attempt (a problem with the network or the other receiver)** ERR-61012(errno=111) [Sender] Failed to connect to the peer server  **When the Receiver is shut down** ERR-6104b(errno=0) [Receiver] REP1 receiver is ended (by thr_exit) Receive and process SR **When the other party normally stopped replication** RECEIVER:REPLICATION STOP MSG arrived! |

The problem of replication Sender/Receiver should be analyzed to determine whether the error was caused by a user-intended command at the recorded time or by a temporary network failure. If the status does not change even with repeated replication restart commands, immediately request technical support from Altibase Technical Headquarters.

Replication Sender/Receiver problems can prevent replication data from being sent, which can make data differ between servers. They can also cause online log files to accumulate on the sender because the sender must retain logs that have not yet been sent, which may lead to a failure on the sender server itself. Therefore, the replication transfer status, called the replication gap, must be monitored.

|  |
| --- |
| ```<br>SELECT REP_NAME,<br>REP_GAP<br>FROM   V$REPGAP<br>;<br>REP_NAME         REP_GAP<br>------------------------------------------------------------------<br>REP1             0<br>1 row selected.<br>``` |

`REP_NAME` is the replication object name. `REP_GAP` is the size from the log record currently being sent to the last log record that has not yet been sent. The default unit is MB.

|  |
| --- |
| ※ `REP_GAP` in Altibase version 6.5.1 or earlier is calculated as follows.<br>Calculate it with the online log file serial numbers `SN` (Sequence Number) and `XSN`.<br>`REP_GAP` (Replication Gap) = [Latest `SN` of local SERVER] - [Latest `XSN` of local SERVER]![replication.png](https://docs.altibase.com/download/attachments/embedded-page/arch/2.%20Procedure%20by%20type%20of%20failure/replication.png?api=v2) |

This value changes continuously while remaining close to zero. If it continues to increase, there may be a Sender/Receiver problem, so check the replication status of each server and the network.

Data conflict due to replication can be checked in `altibase_rp.log` or `altibase_rp_conflict.log` depending on the configuration.

|  |
| --- |
| **In case of PK conflict due to INSERT DML (Dup Error)** ERR-11058(errno=0) The row already exists in a unique index.  **When data is not on the other side by DELETE DML** ERR-61036(errno=0) [Receiver] err_not found in deleteXlog() ERR-61000(errno=0) The received record is not found in the database.  **When data is not on the other side by UPDATE DML (Not Found)** ERR-6103a(errno=0) [Receiver] err_not_found in updateXlog() ERR-61000(errno=0) The received record is not found in the database.  **When the original data differs during UPDATE DML.** ERR-61035(errno=0) [Receiver] An update conflict encountered. ERR-61001(errno=0) A conflict has been occurred while executing the received statement. |

Except for INSERT conflicts, output messages are recorded as two errors for one error. For each data conflict type, the SQL statement that caused the conflict is also logged, which can be important information for finding the corresponding data. This phenomenon occurs because the source data is already different or because servers configured for replication attempt to change data with the same PK without separation. Therefore, review the application execution flow carefully based on the SQL information.
