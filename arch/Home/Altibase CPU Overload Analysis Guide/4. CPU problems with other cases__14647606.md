There are cases where performance is not at the desired level even though CPU is also not being used as much as expected. Consider the following cases for these phenomena.

# 4.1 Mismatch of DB and application program character set

When the character set (`NLS_USE`) setting differs between the DB and the application, Altibase performance can degrade and CPU usage can increase because of internal character-set conversion (encoding). In this case, resolve the problem by matching the character set between the DB server and the application.

```
# Query to check client's NLS_USE
iSQL> select id, comm_name, client_nls from v$session;

#  Query to check DB charset
iSQL> select * from v$nls_parameters;
SESSION_ID : 1
NLS_USE : US7ASCII <---- current client's character set
NLS_CHARACTERSET : MS949 <--- DB server's character set
NLS_NCHAR_CHARACTERSET : UTF8
NLS_COMP : BINARY
NLS_NCHAR_CONV_EXCP : FALSE
NLS_NCHAR_LITERAL_REPLACE : FALSE
1 row selected.
```

# 4.2 Increase of Service Thread

In the Altibase 4.3.x version range, cases have been reported where CPU usage increased because `Select-Poll` system calls increased as `Dedicated Thread` instances increased.

Altibase handles transactions through `Service Thread` instances that manage session connections. When a long-running query occurs or all `Service Thread` instances are in the `Executing` state, Altibase creates new `Dedicated Thread` instances in real time to process new connections or waiting transactions.

Newly created `Dedicated Thread` instances periodically check whether there is a transaction to process. In this process, Altibase issues more `Select-Poll` system calls and `sys(%)` increases within CPU usage.

The DB service thread state can be retrieved with the query below.

```
iSQL> select type,state, run_mode, count(*)
    2 from v$service_thread
    3 group by type,state, run_mode;
TYPE                  STATE       RUN_MODE   COUNT(*)
-----------------------------------------------------------------------
IPC                   POLL        DEDICATED  1
SOCKET(MULTIPLEXING)  EXECUTE     SHARED     1
SOCKET(MULTIPLEXING)  POLL        SHARED     31
3 rows selected.
```

To handle this type of issue, one option is to increase the value of the `MULTIPLEXING_POLL_TIMEOUT` property. This reduces the number of system calls by increasing the execution interval of the `Select-Poll` system call.

Fundamentally, `Dedicated Thread` instances occur because of increased sessions, increased transaction load, many long-running queries, or lock contention. Users should consider improvements that eliminate these root causes.

# 4.3 Effect of OS environment variable setting

CPU usage can change depending on OS environment variable settings. Because Altibase adopts a multi-threaded structure, the related OS settings must be configured properly. These settings should not be understood as settings that reduce CPU usage, but as settings for cases where performance is not proportional to the CPU being used.

For more detailed information, please refer to the "Altibase Installation Guide" provided for each OS.

# 4.4 Frequent DB connection attempts

`V$STATEMENT` in Altibase contains execution information for queries executed by currently connected sessions. Therefore, in an application structure that repeatedly performs connect/disconnect, it is very difficult to find problematic queries from this information.

## 4.4.1 Checking whether frequent DB access occurs

This can be checked with the following query.

```
-- Identify whether frequent connect/disconnect is performed (frequent connect/disconnect causes performance reduction)
SELECT NAME, VALUE FROM V$SYSSTAT WHERE NAME LIKE ‘%logon cum%’;

-- Determine if CPU is used inefficiently by performing repetitive PREPARE process
SELECT NAME, VALUE FROM V$SYSSTAT WHERE NAME LIKE ‘%prepare%count%’;
```

## 4.4.2 Selecting tuning target queries with profiling

Moreover, application performance decreases by the cost of each connect/disconnect. Therefore, it is recommended to change the application structure so that work is processed while connected to the DB. If this is not possible, use the profiling function to find problematic queries, even at the risk of degrading DB performance.

```
ALTER SYSTEM SET TIMED_STATISTICS=1;
ALTER SYSTEM SET QUERY_PROF_FLAG=1;  -- Execute the function
ALTER SYSTEM SET QUERY_PROF_FLAG=0;  -- Terminate the function
```

All queries executed after the above function is enabled are recorded under `$ALTIBASE_HOME/trc/` with file names such as `xxxxx.prof` and the `*.prof` extension. This file is created as a binary file, so the user cannot check it directly. Convert it to plain text as follows.

```
shell>  altiProfile alti-13109987-0.prof > log1.txt
```

`altiProfile` is an analysis utility provided by Altibase. It can be used to create analysis files. Because the file records the executed query statements and detailed execution-time information, problematic queries that took a long time to execute can be found from that information.

For detailed usage of altiProfile, refer to AID's FAQ. (AID description page on how to log queries performed in Altibase: [http://aid.altibase.com/x/ygSL](http://aid.altibase.com/x/ygSL))

Use the profiling function carefully because it can degrade DB performance and can cause disk space shortage due to log recording.
