In general, CPU utilization often increases for a small set of recurring causes. Therefore, checking whether the problem matches a known pattern step by step can be effective.

# 2.1 Has more transaction processing occurred than usual?

If the routine checklist items, such as `Session`, `Service Thread`, and `Prepare/Execute`, all increase while CPU usage increases, this can be considered a normal increase pattern.

Be careful to distinguish the following case from a normal pattern. Service threads may increase because of user-submitted queries or services that have not been verified, such as long-running queries or queries that cause a large volume of change operations.

This type of increase can occur because of the service thread's own load-balancing function.

The pattern itself can be normal, but the cause of the increased query activity still needs to be found. Queries executed manually by users are difficult to detect after the relevant time has passed, so periodically observe the server with the following query to find long-running queries.

```
-- Search for long-running queries whose execution time or result fetch time is 1 second or more
SELECT A.SESSION_ID,
       A.CLIENT_PID,
       B.QUERY,
       B.EXECUTE_TIME,
       B.FETCH_TIME
  FROM V$SESSION A,
       V$STATEMENT B
 WHERE A.ID = B.SESSION_ID
   AND (B.EXECUTE_TIME > 1000000 OR B.FETCH_TIME > 1000000);
```

# 2.2 Has a newly added service (application) occurred?

Because a newly added service is likely to be a direct cause, first analyze the execution plans of newly added queries. Then tune queries with high execution time and high access cost. Periodic observation is needed by using the long-running-query search method described above.

Both of the above cases usually mean that the service application's structure or the queries it executes were implemented inefficiently. For related background, see the CPU usage of Altibase query processing described below.

However, when users check the items in sections 2.1 and 2.2, the most common answer is "No". If there has been no change to the service configuration, the system, or the Altibase version, what is the cause of CPU overload?

To find the problem, analyze the currently running program and DB.

# 2.3 Problem analysis of the application in service

If CPU overload occurs even though there has been no change in the service operation configuration, the increase in data may have exposed a problem that already existed in an existing query.

For example, an index that worked smoothly when the data size was small may become inappropriate as the data size increases over time. In that situation, continued use of the existing index may cause CPU utilization to increase.

# 2.4 Problem caused by query execution cost increase due to query plan change

Altibase 4, Altibase 5, and some Altibase 6 versions (`6.1.1.6.1` or later) automatically execute optimizer statistics collection under certain conditions.

Statistical information is often updated because of data growth or DDL execution, such as an index change. In this case, the query optimizer may occasionally select an incorrect plan with a higher cost than the previous plan while selecting a new query plan.

Queries executed with such an inefficient plan can significantly increase access cost and cause CPU usage to increase. In many cases, the problem query is found with the long-running-query search query described above.

Therefore, when an abnormal CPU usage pattern occurs, it is effective to check the long-run query first with the monitoring query.

For an identified long-running query, check whether there is a problem with the plan by executing the command that shows the execution plan, or by querying the runtime plan stored in `V$PLANTEXT`.

To check query status, run the query status check query described in the "Altibase Monitoring Guide" document.
