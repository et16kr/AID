This chapter briefly describes where Altibase uses CPU during query processing.

# 3.1 CPU load according to application program implementation type

Altibase query processing is largely executed through the following processes.

1) Check sentence/grammar errors in the query

2) Check the existence of table/column used in the query

3) Establish an optimal execution plan

4) Access the data area and acquire or change data with the required operations

Among these processes, 1) through 3) are called Prepare-Validation-Optimization (PVO), and process 4) is called EXECUTE. In general, PVO accounts for about 60% to 70% of the entire query processing cost.

Based on the assumption above, repeatedly executing the same query in a `PREPARE-EXECUTE` pattern can be expected to cause inefficient CPU usage. Therefore, if the following values increase excessively in `V$SYSSTAT`, developers or operators should modify the application so that it does not repeatedly perform `PREPARE`, or should use the `PLAN-CACHE` function provided from Altibase 5.

```
iSQL> SELECT * FROM V$SYSSTAT WHERE NAME LIKE '%prepare%count%';
SEQNUM      NAME                            VALUE
---------------------------------------------------------------------
37          prepare success count           25522
38          prepare failure count           56
```

If the above values continue to increase significantly, part of the application is repeatedly performing `PREPARE`. The application can be found by combining `V$SESSTAT`, another performance view that shows `V$SYSSTAT` information in detail by session, with the `V$SESSION` table, which shows the process PID.

For more detailed information related to the above, refer to the "Altibase Development Guide".

# 3.2 CPU Load by Data Scan

## 3.2.1 **Data access of memory table**

Altibase's memory table is kept loaded in the physical system memory. The unit to be stored is stored in a page unit of 32Kbyte, and even within this page, it is divided into individual units (Slot) for each table suitable for record storage.

The problem is, when accessing a table in a full-scan format, the cost of accessing all the data in the table is very high. If such queries are executed in multiple sessions at the same time, the CPU usage rate will inevitably increase.

So, when using an index, does the CPU utilization necessarily decrease?

Not necessarily. The index of the memory table also exists in system memory. However, the memory table index does not contain the actual data value. Instead, it has the physical pointer value for the data location in system memory, and this pointer value is calculated with the index key value and stored in sorted converted-value form.

Therefore, the actual physical data indicated by the index is accessed every time to obtain and compare the data value. (This process may seem unreasonable, but it does not induce disk I/O in terms of performance, so it is possible to process more transactions by occupying the CPU even when other DBMSs require waiting time due to I/O.)

Therefore, even for queries using indexes, the CPU usage rate increases as the number of access-cost increases. Therefore, the user must make efforts to remove inefficient queries by monitoring the execution plan of queries executed in a service operation on a regular basis.

## 3.2.2 **Data access of disk table**

Understanding CPU usage for disk tables requires understanding CPU use on the I/O path. In general, an OS allocates a memory area called file cache and keeps frequently accessed file I/O data loaded in memory to preserve I/O performance. However, most RDBMS products achieve this effect by placing their own buffer in the middle, so if the file system supports Direct I/O, it is generally recommended to use Direct I/O instead of the file cache.

Buffered I/O uses CPU resources for read/write system-call processing in application code, and CPU resources are also consumed when the OS synchronizes file-cache contents to disk. At this point, the process waits until the I/O operation completes and CPU utilization may appear to decrease. However, service throughput can decrease because other applications cannot use those CPU resources during that time.

Conversely, when Direct I/O is used, the CPU delegates the I/O itself to the dedicated I/O channel. As a result, the CPU does not need to wait for I/O processing, other applications can use the resource, and the service can process relatively more work. However, compared with Buffered I/O, users may interpret the CPU usage rate as having increased.

For more detailed information on how to configure and operate Buffered I/O and Direct I/O, refer to the "Volume Configuration Guide Considering Disk I/O Bottleneck".

In summary, there is no single answer for whether Buffered I/O or Direct I/O is appropriate because both have trade-offs for CPU usage and performance. Configure them appropriately for the user's service environment.

# 3.3 Summary

All of the processes described above require CPU resources. Therefore, it is conceptually impossible for query processing itself to use little CPU while also producing high performance. However, users and developers can make Altibase use CPU efficiently while delivering the required performance.
