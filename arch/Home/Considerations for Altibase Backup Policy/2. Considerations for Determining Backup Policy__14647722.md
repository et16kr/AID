# 2. Considerations for Determining Backup Policy
Source: https://docs.altibase.com/display/arch/2.+Considerations+for+Determining+Backup+Policy
Updated: 2025-09-23T10:05:01.000+0900

- [Select backup target](#id-2.ConsiderationsforDeterminingBackupPolicy-Selectbackuptarget) - [Recovery point](#id-2.ConsiderationsforDeterminingBackupPolicy-Recoverypoint) - [Recovery time](#id-2.ConsiderationsforDeterminingBackupPolicy-Recoverytime) - [Backup performing time](#id-2.ConsiderationsforDeterminingBackupPolicy-Backupperformingtime) - [Backup copy storage cycle](#id-2.ConsiderationsforDeterminingBackupPolicy-Backupcopystoragecycle) - [Configuring disk partitions for backup](#id-2.ConsiderationsforDeterminingBackupPolicy-Configuringdiskpartitionsforbackup)

Selecting the backup policy should be decided in consideration of the operation environment, such as the importance of data, recovery policy, and backup size. This chapter describes the considerations for determining a backup policy.

# Select backup target

---

To define a backup policy, first select the backup target. Then, considering the characteristics of the backup target, determine the recovery policy, backup type, backup cycle, backup time, and retention period for backup files.

This backup plan is not something a DBA can establish alone. Cooperation from the business owner or data owner is required because they best understand the characteristics of the backup target.

# Recovery point

---

The available recovery point differs by backup type. Determine an acceptable recovery point based on the importance of the backup target, then select a backup method accordingly.

There are three major recovery points.

| Recovery point | Description |
| --- | --- |
| Backup point | This refers to the restoration to the point in time when the backup was performed. |
| Complete recovery | This refers to the restoration to the most recent point in the database.<br>This is possible only when online log files and archive log files are not lost. |
| Incomplete recovery | This refers to the restoration to a certain past point in time.<br>Incomplete recovery is possible at two points in time.<br>- UNTIL CANCEL<br>Recover by specifying a specific log file<br>- UNTIL TIME<br>Recover by specifying the date and time |

The table below summarizes the recovery points by backup type. Select a backup method suitable for the backup target by referring to the table.

| Backup type | Method | Backup point | Complete recovery | Incomplete recovery |
| --- | --- | --- | --- | --- |
| Logical backup | - | Possible | N/A | N/A |
| Physical backup | Online backup | Possible | Possible | Possible |
| Physical backup | Offline backup | Possible | N/A | N/A |
| Incremental backup | - | Possible | Possible | Possible |

# Recovery time

---

Recovery must be performed after service interruption. In operating environments where service downtime must be minimized, recovery time must also be considered when determining the backup policy.

Since the factors that affect the recovery time differ depending on the backup type, please refer to the table below and select the method that suits the characteristics of the backup target.

| Backup type | Method | Factors affecting recovery time | Description |
| --- | --- | --- | --- |
| Logical backup | aexport | - Number of database objects | If creating objects is necessary during the recovery process, the number of objects can affect recovery time. |
| Logical backup | iLoader | - Number of tables<br>- Data usage of tables<br>- Number of indexes | Since the contents of the file are read and inserted into the table, the number of tables, records, and indexes affects recovery time. |
| Physical backup | Online backup | - Data usage of memory tables<br>- Memory index<br>- Number of log files | Recovery is performed during the Altibase server startup process. It takes time to load memory table data into memory and rebuild memory indexes. Since log files are used in recovery, the number of log files to apply affects recovery time. The number of log files is determined by the amount of transactions that occurred after the backup. |
| Physical backup | Offline backup | - Data usage of memory tables<br>- Memory index | Recovery time is shortest because Altibase starts and recovers using only the backup files.<br>When the Altibase server starts, it still takes time to load memory table data into memory and rebuild memory indexes. |
| Incremental backup | - | - Data usage of memory tables<br>- Memory index<br>- Number of log files | During recovery, it takes time to load memory table data into memory and rebuild memory indexes. Since log files are used in recovery, the number of log files to apply affects recovery time.<br>The number of log files is determined by the amount of transactions that occurred after the backup. |

# Backup performing time

---

Backup execution takes longer as the database becomes larger, and transactions are affected while backup is running. Therefore, it is recommended to perform backups during the most idle time in Altibase operation.

This table summarizes the factors that affect the backup time by backup type and how they affect transactions.

- ### Backup time

  | Backup type | Method | Factors affecting backup time | Description |
  | --- | --- | --- | --- |
  | Logical backup | aexport | - Number of database objects | Since object creation scripts are generated, backup time is affected by the number of database objects. |
  | Logical backup | iLoader | - Number of tables<br>- Usage of tables | Since text files are created by querying data for each table, backup time is affected by the number of tables and the amount of table data. |
  | Physical backup | Online backup | - Size of disk table data files<br>- Size of memory checkpoint image files | Online backup physically copies data files, so data file size affects backup time. |
  | Physical backup | Offline backup | - Size of disk table data files<br>- Size of memory checkpoint image files | Offline backup also physically copies data files, so data file size affects backup time. |
  | Incremental backup | Level 0 incremental backup | - Size of disk table data files<br>- Size of memory checkpoint image files | Level 0 incremental backup is similar to online backup, so data file size affects backup time. |
  | Incremental backup | Level 1 incremental backup | - Amount of data page changes | Level 1 incremental backup time is affected by the amount of data page changes caused by change transactions. |

- ### Transaction

  This table compares the impact on transactions when performing a backup.

  | Backup type | Method | Impact on transactions |
  | --- | --- | --- |
  | Logical backup | aexport | DDL cannot be performed temporarily. |
  | Logical backup | iLoader | Memory GC increases during backup. |
  | Physical backup | Online backup | Online log files increase because checkpoints cannot run during backup. |
  | Physical backup | Offline backup | Service downtime is required. |
  | Incremental backup | - | Routine DB performance degradation occurs due to activation of the 'Page Change Tracking' feature.<br>Online log files increase because checkpoints cannot run during backup. |

# Backup copy storage cycle

---

It is recommended to keep at least two backup copies.

This is to prepare for the loss of backup copies due to an incorrect backup or a disk fault or user fault.

# Configuring disk partitions for backup

---

If backup files are stored on disk, set the backup location to storage space that is physically separated from the paths where database data files and log files are located.

During database operation, disk I/O occurs as follows. An exception is a service in which mainly read-only transactions occur on memory tables.

- Disk I/O for log files where changes to the database are recorded
- Disk I/O to record to the memory checkpoint image file in the memory table
- Disk I/O to read and record data files in the disk table

Therefore, separate the disk space to minimize bottlenecks between disk I/O during database operation and disk I/O during backup execution.
